## 1. Transactions & isolation

- Keep transactions **short** and never hold one open across network calls (HTTP to payment provider, sending email, waiting on a queue). Do external work before or after, coordinate with an outbox or state machine.
- Defaults: Postgres = READ COMMITTED; MySQL InnoDB = REPEATABLE READ (with gap/next-key locks that can surprise people); Mongo = snapshot inside multi-doc transactions.
- Isolation anomalies to look for:
  - **Lost update** (read value, compute, write back): use atomic `UPDATE … SET x = x + 1`, `SELECT … FOR UPDATE`, or optimistic version column.
  - **Write skew** (two transactions each check a condition over a set, then both write): needs SERIALIZABLE, a constraint, or locking a shared row.
  - **Check-then-insert** duplicates: unique constraint + `INSERT … ON CONFLICT` (PG) / `INSERT … ON DUPLICATE KEY UPDATE` (MySQL) / `updateOne(..., {upsert: true})` with unique index (Mongo).
- Under SERIALIZABLE (PG) or with deadlocks anywhere, the app **must retry** on serialization failure (`40001`) / deadlock (`40P01`, MySQL 1213). Make transaction bodies safe to re-run.
- Set `lock_timeout` / `statement_timeout` (PG) or `innodb_lock_wait_timeout` / `max_execution_time` (MySQL) so stuck work fails fast instead of piling up.

## 2. Concurrency patterns

- **Atomic conditional update** (best default):
  `UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1` → check rows affected.
- **Pessimistic lock**: `SELECT … FOR UPDATE` when you must read then decide. Lock rows in a **consistent order** (e.g. by id) to avoid deadlocks when locking multiple rows.
- **Optimistic lock**: `version` column; `UPDATE … SET …, version = version + 1 WHERE id = $1 AND version = $2`; 0 rows → conflict → reload/retry or report to user. Most ORMs support this natively (JPA `@Version`, Rails `lock_version`, SQLAlchemy `version_id_col`).
- **Job queues in SQL**: `SELECT … FROM jobs WHERE status='pending' ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED` (PG 9.5+, MySQL 8.0+), with a partial index on pending rows.
- **Advisory locks** (PG `pg_advisory_xact_lock`, MySQL `GET_LOCK`) for coordinating work that isn't tied to a row; prefer transaction-scoped variants so they release automatically.
- **Inventory / seat booking**: atomic decrement with a `CHECK (stock >= 0)` constraint as a backstop; or reservation rows with a unique constraint.

## 3. ORM pitfalls

- **N+1 queries**: loading a list and then lazily touching a relation per item. Fixes: Django `select_related` (FK/1-1, JOIN) / `prefetch_related` (M2M/reverse, second query); SQLAlchemy `joinedload` / `selectinload`; Rails `includes`/`preload`; Prisma `include`; TypeORM `relations` / query builder joins; GORM `Preload`. Detect with query logging/counting in tests (django-assert-num-queries, `bullet` gem, SQLAlchemy event listeners).
- **Loading whole objects to update one field** → use bulk/targeted `UPDATE` (`QuerySet.update()`, `update_all`, `session.execute(update(...))`).
- **Row-by-row inserts in a loop** → batch (`bulk_create`, `insert_all`, `executemany`, multi-row `INSERT`, `COPY` for large loads).
- **Implicit transactions/autocommit** confusion — be explicit about transaction boundaries (`transaction.atomic()`, `session.begin()`, `prisma.$transaction`).
- **Lazy loading after session close** (SQLAlchemy `DetachedInstanceError`, Hibernate `LazyInitializationException`) — load what you need inside the unit of work.
- **ORM-generated `OFFSET` pagination** and `COUNT(*)` on every page — see query-optimization.md.
- **Migrations generated by the ORM** may be unsafe on big tables (e.g. adding a column with a volatile default, creating non-concurrent indexes, renames). Review generated SQL (`sqlmigrate`, `alembic upgrade --sql`, `prisma migrate diff`) before deploying.
- Raw SQL is fine for hot or complex paths. Always parameterize — never string-concatenate user input (SQL/NoSQL injection, including Mongo operator injection via `{ "$gt": "" }` in JSON bodies).

## 4. Connection pooling

- DB connections are expensive (Postgres: one process each, ~5–10MB+). Total connections = app instances × pool size (+ workers, cron, migrations). Keep it well under `max_connections`.
- Rough pool size per instance: small (10–20) is usually right; more connections than ~2–4× DB CPU cores mostly adds contention.
- Use **PgBouncer** (transaction mode) or RDS Proxy for many app instances or serverless. Transaction mode breaks session state: session-level prepared statements (older drivers), `SET` without `LOCAL`, advisory session locks, `LISTEN/NOTIFY`, temp tables.
- Serverless (Lambda, Vercel): open connections outside the handler, use a proxy or HTTP-based driver (Neon, PlanetScale, Data API).
- Configure acquire timeout, idle timeout, max lifetime (shorter than any LB/firewall idle cutoff), and health checks. Watch for pool exhaustion caused by leaked connections or long transactions.

## 5. Idempotency & outbox

- **Idempotency keys** for retried writes (payments, order creation): table with `UNIQUE (client_id, idempotency_key)` storing the response; insert it in the same transaction as the business write.
- **Transactional outbox**: write the domain change and an `outbox` row in one transaction; a relay publishes outbox rows to the broker and marks them sent. Avoids "DB committed but event lost" and "event sent but DB rolled back." Consumers must be idempotent (dedupe by event id).
- Never do "write to DB, then publish to Kafka" as two independent steps without one of these patterns.

## 6. Caching

- Cache-aside with TTL is the default. Invalidate on write (delete key after commit, not before). Beware stampedes on hot keys: request coalescing, jittered TTLs, or early refresh.
- Cache derived/expensive reads, not as a fix for a missing index.
- Redis is not durable by default in the way a DB is; don't make it the system of record unless persistence (AOF) and failover semantics are understood.

## 7. Code structure & testing

- Keep data access behind a repository/DAO layer with intention-revealing methods (`reserve_stock(sku, qty)`), so transaction and locking logic lives in one place.
- Test against the **real engine** (Testcontainers, docker-compose) — SQLite/H2 in tests hides constraint, locking and SQL dialect differences.
- Write concurrency tests for critical invariants: run N parallel workers against the same row and assert the invariant holds.
- Assert query counts on key endpoints to catch N+1 regressions.
